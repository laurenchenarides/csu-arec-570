Reproducibility starts with organization

Can another researcher reconstruct a result from the same inputs?

They need

  • Original inputs
  • Code for every transformation
  • The order in which the code runs
  • Software and package requirements
  • The project version used for the result

Source: Gentzkow and Shapiro (2014)

What version control adds

Version control records selected states of a project and the changes connecting them

A useful history can answer

  • What changed
  • Who made the change
  • When the change was recorded
  • Why the change was made
  • Which version produced a reported result

Git, GitHub, and RStudio have different roles

Tool Role in the workflow
Git Records file changes and commits on the computer
GitHub Hosts a remote copy and supports sharing and collaboration
RStudio Provides buttons and menus that run Git commands

Git supplies the version history. GitHub gives that history an online location

A repository is the project and its history

A repository contains

  • The working files currently visible in the project folder
  • A hidden .git directory containing the local history
  • Optional connections to remote repositories such as GitHub

The project folder becomes a Git repository when Git is initialized or when a repository is cloned

Three locations in the workflow

Working files              Local Git history              GitHub repository
on your computer           on your computer               online remote

edit files  --commit-->    saved checkpoints  --push-->  shared checkpoints
            <--restore--                       <--pull--

A commit saves to the local history. A push sends local commits to GitHub

Create a repository for your research

Use create when the project belongs to you or your research team

For an existing RStudio project

usethis::use_git()
usethis::use_github(private = TRUE)

Review .gitignore before the first commit. Keep restricted or licensed data outside GitHub

Clone a repository you can access

Use clone when the remote repository already exists and you need a local working copy

In RStudio

  1. Copy the repository’s HTTPS URL from Code
  2. Select File > New Project > Version Control > Git
  3. Paste the URL and choose a parent folder
  4. Select Create Project

Cloning copies files, branches, and history and configures the remote as origin

Fork a repository into your account

Use fork when you want a linked copy of another person’s repository under your GitHub account

A fork supports

  • Pulling later updates from the original repository
  • Making changes in a repository you own
  • Proposing changes to the original repository in a pull request

For this course, fork the demo so you can receive updates across Lectures 5.3 to 5.5

Use a template for an independent project

Use template when the files provide a useful starting structure for a new project

The new repository receives

  • The template’s files and folders
  • A new history beginning in the new repository
  • The visibility setting you choose

This is useful for a lab project layout or a standard replication package

Git records changes through three states

State Meaning
Working directory Files currently being edited
Staging area Changes selected for the next commit
Commit A recorded snapshot with an explanatory message

Staging lets one work session become several coherent commits

Read the RStudio Git pane

Status Meaning
M A tracked file was modified
? A new file is untracked
A A new file is staged for its first commit
D A tracked file was deleted
R A tracked file was renamed or moved

Diff shows changed lines. The Staged boxes select files for the next commit

The everyday Git loop

  1. Pull before beginning a work session
  2. Make one coherent change
  3. Inspect the changed lines with Diff
  4. Stage the files that belong to the change
  5. Write a specific commit message and select Commit
  6. Push the commits to GitHub

Repeat the edit, inspect, stage, and commit steps as the work develops

Write commit messages for future readers

General message Research-specific message
updates Code suppressed ACS estimates as missing
fixed bug Keep FIPS codes as text to preserve leading zeros
final version Restrict sample to the April-September growing season

A useful message identifies the completed change. Add an explanation when a change alters the sample or interpretation

Pull and push move commits

Pull brings remote commits into the local repository

Push sends local commits to the remote repository

When a push is rejected because the remote has newer commits

  1. Pull the remote commits
  2. Review any conflicts Git reports
  3. Complete the merge if required
  4. Push the combined history

What belongs in the repository

Track files that explain or implement the research

  • Source code
  • README files and project documentation
  • Data dictionaries and retrieval logs
  • Small configuration files without credentials
  • Manuscript and presentation source files

Commit generated outputs when the research team or publication process requires them

What belongs outside the repository

Common exclusions in .gitignore

  • API keys and credentials such as .Renviron
  • Confidential or restricted data
  • Large source files stored in an archive
  • Derived files rebuilt by code
  • R session files such as .RData and .Rhistory

.gitignore applies to files Git has not started tracking

Check before the first commit

Open .gitignore and git status before staging a new project

Ask

  • Does any file contain a password or API key
  • Does the project contain restricted or licensed data
  • Is a large file available from a stable archive or reproducible download
  • Can a derived file be rebuilt by the project scripts
  • Does each tracked file help explain, run, or report the research

Revoke any credential that enters a commit because earlier commits retain the file contents

Common problems and first checks

Problem First check
The Git tab is missing Confirm that the .Rproj inside a Git repository is open
Git rejects a commit Check the configured name and email with usethis::git_sitrep()
GitHub rejects authentication Check whether the personal access token is present and current
A push is rejected Pull and inspect the incoming commits
A file never appears in the Git pane Check the patterns in .gitignore

Record the exact error message when asking for help
